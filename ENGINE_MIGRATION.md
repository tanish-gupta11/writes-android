# Writes engine migration: audit and implementation gates

Assessment date: 2026-10-02. Status: feasibility checked; no replacement engine integrated. Writes 0.6.0 and its private signing material remain unchanged. This document corrects the supplied AI work orders; their predictions are not evidence of working features.

## Verified starting point

- Source and release signing files exist locally. Do not replace the signing key, clear the main app, or publish signing material. The working tree contains uncommitted 0.6.0 work: preserve it before migration.
- Authorized Android device is arm64-capable, API 36. Existing tests cover one device only.
- Ubuntu runs under WSL2, x86_64, reporting Ubuntu 26.04.1, not the suggested 22.04/24.04. A build against this distribution has not been qualified.
- Host reports about 13.94 GiB usable physical RAM and 8 logical processors. WSL currently reports 6,901 MiB RAM and 2,048 MiB swap. Git is present; Linux Java, javac, gcc/g++, make and the queried autotools were not found on PATH. The conventional Linux Android SDK directory was absent.
- Windows C: has about 135.8 GiB free. WSL's virtual filesystem reports much more free space; that must NOT be treated as extra physical capacity. Verify where the VHD is stored before estimating a build budget.
- No bulk source download, dependency install, WSL restart/configuration change, licence change or external publication was performed during this assessment.

## Corrections to the proposed architecture

1. **A real engine is the right direction, but embedding is a project, not a dependency toggle.** Current [Collabora Android instructions](https://www.collaboraoffice.org/post/build-code-android/) use the Gerrit `online` monorepo with the native engine in `engine/`, then native application components and the Gradle Android project. The old separate-core recipe is outdated for current main. Remote main resolved to `2f38e5d87257aa2a6a0f94401a259f7792b0c1ca` during this assessment; this is an observed reference, NOT a tested release pin. Select and record a coherent source revision and toolchain before building.
2. **“Exact-layout PDF to DOCX” is unproven.** LibreOffice lists distinct [PDF import and Writer export filters](https://help.libreoffice.org/latest/en-US/text/shared/guide/convertfilters.html). Their existence does not demonstrate that importing a PDF into Draw and saving DOCX yields an editable, faithful Word file. Prove the chosen route on device before exposing it. Raster pages inside DOCX are visual references, not editable reconstruction. Never label the conversion lossless without evidence.
3. **Offline use and no INTERNET permission are separate requirements.** The current [upstream Android manifest](https://raw.githubusercontent.com/CollaboraOnline/online.mirror/main/android/app/src/main/AndroidManifest.xml) requests INTERNET and broad storage access. A fork must audit/remove unnecessary permissions and test local functionality without network access; copying upstream does not meet the supplied policy automatically.
4. **Free sharing is not licence-free.** [MuPDF's Android documentation](https://mupdf.readthedocs.io/en/latest/guide/using-with-android.html) requires compatible licensing and complete app source availability for its open-source route; otherwise Artifex offers commercial licensing. An About screen alone is insufficient. Decide the distribution model with the owner before integration. Preserve required legal notices while replacing product branding; do not interpret “remove all trademarks” as permission to erase copyright/attribution notices. Review each component's actual licence and compatibility, not just its headline licence name.
5. **Engine functions are not finished app features.** PDF editing, secure redaction, form support and signatures need UI, persistence and interoperability tests. A handwritten signature image is not a certificate-backed digital signature. A black rectangle is not redaction. Compression must report quality trade-offs and may not reduce every file.
6. **OCR needs bundled models and measured accuracy.** [Tesseract4Android](https://github.com/adaptech-cz/Tesseract4Android) supports native OCR with separate language data. Pin/checksum the library and English/Hindi models, account for their licences and storage, and test recognition and cancellation. OCR does not itself reconstruct Word tables or layout.
7. **Time, RAM and APK size claims are estimates.** The supplied 150–250 MB and multi-session predictions have not been measured here. Current WSL RAM is below that work order's suggested build budget. A conservative low-parallelism build might be possible, but should not be promised or started with unconstrained parallelism. Account for Windows/Docker workloads; do not shut them down without approval.

## Implementation gates

1. **Owner decision:** free, source-sharing distribution versus a closed-source distribution strategy. Private user documents, credentials and signing keys are never corresponding source and must stay private. No automatic public repository upload.
2. **Build prototype:** preserve the current source/APK baseline; prepare an isolated Linux build directory, resolve dependencies and pin versions/checksums. Build an arm64 engine prototype in a separate QA package. Record build errors and resource use. No fallback to the old editor disguised as successful engine integration.
3. **Document vertical slice:** open a representative DOCX containing tables, pictures, comments, tracked changes, headers/footers and footnotes; edit and save it with the new engine; reopen it in desktop Word. Test printing, offline operation, source immutability and draft migration. Keep unsupported features explicitly unverified.
4. **PDF/OCR slices:** independently test rendering, selected edits, forms, redaction, page tools and OCR. Match saved PDF output against independent readers. Verify redacted information cannot be extracted from saved bytes, not merely hidden on screen.
5. **Conversion gate:** compare every page of approved fixtures, including the local 19-page PDF. Record text/spacing/order, editable object structure, source/output page count and rendered differences. Include scanned, multi-column and table-heavy cases. Keep private fixtures outside the repository.
6. **Release qualification:** regression plus crash/process-death/storage interruption tests; low-memory and large-file workloads; accessibility/RTL/font coverage; native 16 KiB page-size compatibility; security/dependency review; licence/source distribution bundle; upgrade using the existing key. Device passes alone do not prove Word/Acrobat parity.

Until these gates pass, the production blockers in RELEASE_CHECKLIST.md remain in effect. This assessment does not create a new APK or justify calling the existing APK production-ready.
